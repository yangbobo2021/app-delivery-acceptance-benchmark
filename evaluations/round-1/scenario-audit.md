The generated lists cover the main operations, distinct-item identity, persistence/isolation, validation and data-integrity clauses in the original requirements. No scene was added merely to fill P2 or P3. Empty P3 is reasonable because the source requirements contain no cosmetic-only obligation. The absence of P2 in Go and Electron is not by itself a failure, although the narrow legal-ID and whitespace/special-text cases deserve a second look for importance calibration. The major defects below matter more than the distribution itself.

## Findings by project

**Python CLI.** `INV-05-S02` is P1 despite testing whether processing can alter the original invoice CSV or any sibling file, including transient writes. That is a source-data integrity risk with no verified safeguard. Under the current priority standard, its loss/corruption consequence supports P0; leaving it outside P0 allows a P0-only run to miss a major risk. The remaining requirement-owned sets have distinct purposes: valid/invalid CSV, exact arithmetic, output and error contracts, working-directory independence and case-sensitive repeatability. `INV-02-S03` uses a very large legal sum, but the accuracy risk justifies considering impact rather than demoting it solely because the input is uncommon.

**Go HTTP service.** `STOCK-04-S02` and `STOCK-04-S03` are P1 even though overselling under concurrent distinct requests or double deducting one request ID could violate the inventory integrity invariant. Both merit P0 consideration as major risks. `STOCK-02-S04` tests invalid request IDs under the valid-reservation requirement; this is owned by `STOCK-05`. The `STOCK-05` list omits that class, so the combined catalog contains it but a per-requirement audit and execution plan can miss it. `STOCK-03-S02` and `S03` share a retry shape but target different failure mechanisms (response replay after balance changes versus retry after exhaustion), so they are not redundant by default.

**TypeScript browser app.** P0 covers add, toggle, filtering, deletion/persistence and script execution; P1/P2 cover special input and interaction states. `TODO-01-S03` rejects both an empty string and a spaces-only title but explicitly requires a visible error only for the latter. The original wording applies visible feedback to an all-blank title, which includes the empty string; an implementation silently rejecting `""` could pass this scene. The issue is a missing assertion within a useful scene, not a missing whole requirement. `TODO-05-S03` combines many mutations in one P0 persistence case, increasing diagnostic cost; its purpose is still coherent.

**Electron desktop app.** P0 includes ordinary note operations/persistence and the major script, Node and path-escape risks. `NOTE-04-BB-004` puts direct renderer access to Node `process` in P1 while `NOTE-04-BB-003` puts `require` and filesystem access in P0. `process` can expose runtime data and capabilities; the split is not adequately justified and should be reconciled for consistent risk grading. `NOTE-05-BB-001` asks to try an unspecified data-access entry outside the declared IPC interface. The original restriction is important, but this black-box scene has no concrete alternate entry or independent observable oracle; it risks a blocked or superficial test. `NOTE-03-BB-004` repeats many save/edit/delete operations across both user-data directories; the isolation purpose is valid but the scope is larger than necessary.

These findings are retained against exact scene IDs. This round does not rewrite frozen scenario outputs or change the generator's workflow. Before executing the second scene in each project, choose a non-injected P0 scene whose oracle is concrete and whose test path is distinct from the seeded defect. The selected two scenes per project are a deliberate sample, not a claim that all 91 generated scenes passed.
